The Challenge-Grill Method: Interview Your Way to the Fix

Reading a case study tells you what went wrong. Grilling tells you what to build. Here is how to repoint Matt Pocock's Grill Me prompt at any of the 22 challenges — and let the answers write your Spec Doc and gates for you.

🌱 Beginner⏱ ~1 min

1. The Missing Middle Step

Every dashboard that fails starts the same way: a person with a problem jumps straight to code. Part 7 fixed that for build requests — the AI refuses to code until it has grilled you. But a challenge is a different object. "Latent pipeline failure" or "confirmation bias" can't be answered with "1 Agree" to generic questions; the interview must interrogate where the failure enters your specific data, and what evidence on the chart proves it's gone.

Challenge card→ 🤺 Grill it→ Spec Doc→ Derived gates→ Build→ Self-grade

Without the griddle step, students guess the design, then tick rubric boxes about an artifact nobody specified — Part 7's "vague prompt → drift" failure, reappearing in the grading stage.

⚡ Intermediate⏱ ~1 min

2. The Challenge-Grill Prompt

Paste this after Part 7's system prompt (or use it standalone). Fill in the one bracket: your chosen challenge.

challenge_grill_prompt.md 
SYSTEM INSTRUCTION: Challenge Grill — Visualize the Fix, Not the Feature

You are still the adversarial Data Visualization Architect from the Grill Me
method, but today's object of interrogation is a KNOWN FAILURE MODE, not a
build request.

CHALLENGE DECLARED: [e.g., Challenge #6 — Latent Data Pipeline Failure,
Public Health England .xls truncation, 2020]

Apply the original Rules of Engagement (decision tree, 3-4 dependent
questions per round, recommended defaults), and add three frontiers:

FRONTIER A — FAILURE ANATOMY:
- Where does this failure enter MY pipeline: source → aggregate → render?
- Which real case does mine resemble, and what would mine look like?

FRONTIER B — DESIGN DECISIONS:
- What on-chart element makes the failure VISIBLE or IMPOSSIBLE
  (annotation, band, second panel, label)? Recommend a concrete default.

FRONTIER C — GATE DERIVATION:
- For every Spec decision I approve, emit ONE boolean gate
  ("yes/no, checkable on the artifact") that would FAIL if the decision
  were drifted away from.

Output: a Spec Doc excerpt (my decisions, numbered) + my challenge gates.
Begin with Frontier A, Question 1.
The One-Line Addition

If you only remember one thing: end every approved decision with "and give me the gate that fails if this is ignored." That single sentence chains Spec Doc → rubric, so your self-grading stops being opinion and starts being verification.

🔥 Advanced⏱ ~2 min

3. Watch a Grill: Challenge #1 → Gates

Student scenario: "I'm building a storm-prep map for my town's emergency page." Declared challenge: #1 Uncertainty & Risk Representation (Hurricane Dorian, 2019).

❓ Round 1 · Q1: Boundary Semantics
Context: Dorian residents outside the drawn cone assumed safety. What does your boundary actually represent?
➡️ Recommended: Render the 66% probability area as a shaded band (not a line) and print "66% probability of center-track" on the chart.
Student: "1 Agree." → Spec decision D1: shaded band + probability label.
❓ Round 1 · Q2: The "Outside = Safe" Illusion
Context: The failure mode is binary thinking. How does the design attack it?
➡️ Recommended: Add a persistent banner: "Impacts — rain, wind, storm surge — extend BEYOND this band" and a second lighter 90% ring.
Student: "1 Agree." → Spec decision D2: banner + 90% outer ring.
❓ Round 2 · Q3: Evidence Placement (F-Pattern)
Context: Where do D1/D2 live so a panicking reader sees them first?
➡️ Recommended: F-Top stem: probability label as a KPI callout; banner directly under it; the map (F-Mid) is secondary to the meaning.
Student: "1 Agree." → Spec decision D3: label + banner above the map.
❓ Round 2 · Q4: Gate Derivation
Context: Approve decisions, then derive the boolean gates that fail on drift.
➡️ Recommended gates: G1 = boundary is a shaded band AND carries a printed probability %; G2 = "beyond the band" warning present; G3 = shading is CVD-safe (Okabe-Ito blue + hatch, never red/green alone).
Student: "1 Agree." → Spec Doc excerpt complete → build → self-grade.
derived_spec_excerpt.md 
# SPEC EXCERPT — Challenge #1 Fix (storm-prep map)
## DECISIONS (from grill, numbered)
D1: Uncertainty rendered as shaded 66% band, labeled on-chart.
D2: Outer 90% ring + "impacts extend BEYOND this band" banner (F-Top).
D3: Label & banner placed above the map (F-Pattern top stem).
D4: Band uses #0072B2 fill + diagonal hatch (CVD + non-color redundancy).

## CHALLENGE GATES (boolean, self-graded)
[ ] G1: Shaded band present AND probability % printed on the chart.
[ ] G2: "Beyond the band" warning visible without hovering.
[ ] G3: Band encoding is not color-alone (hatch/label redundancy).
[ ] G4: grader/grader.v2.js on my artifact → 4/4.

## LOOP CLOSES
G1-G3 graded by me against the artifact; G4 graded by the (validated) machine.

🔑 Key Takeaways

  • Recognition ≠ design. The grill is the step that converts a case study into architecture.
  • Point the Part 7 prompt at a declared failure mode: Frontiers A (anatomy) → B (design) → C (gates).
  • "Give me the gate that fails if this is ignored" is the sentence that links Spec Doc to self-grading.
  • Spec first, code second, grade last — the student does two of the three checks; the machine does the third.
